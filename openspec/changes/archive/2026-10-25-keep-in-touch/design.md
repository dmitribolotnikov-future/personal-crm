# Design

## Context

Мотивация - в `proposal.md`, требования - в `specs/keep-in-touch/spec.md`.

Что есть сейчас:

- Таблицы `contacts` и `notes` (`src/db/schema.ts`). У заметки есть `created_at` - момент, когда её написали; `updated_at` меняется при правке текста. Заметки удаляются вместе с контактом (`ON DELETE CASCADE`), есть индекс `notes_contact_id_idx`.
- Формы контакта (добавление и изменение) - один компонент `src/components/contact-form.tsx`. Поля перечислены в `contactFields` (`src/lib/form-state.ts`), значения приходят строками и проверяются `contactSchema` (`src/lib/validation.ts`), пустая строка превращается в `null`.
- Серверные действия в `src/app/actions.ts` после любой записи вызывают `revalidateAll()`, так что главная и карточки обновляются при следующем открытии.
- Чтение данных в `src/lib/data.ts`; каждая функция вызывает `connection()`, поэтому страницы считаются на каждый запрос - «сегодня» всегда свежее.
- Даты заметок форматируются на сервере (`src/lib/format.ts`) в часовом поясе сервера; часовой пояс нигде явно не задан.
- Тестов и тест-раннера в проекте нет. Есть `tsx` и Node.js 24.
- В `src/components/ui/` нет компонента выпадающего списка или переключателя.

## Goals / Non-Goals

**Goals:**

- Вся логика сроков - в одном чистом модуле без обращения к базе, чтобы карточка и блок считали одинаково и её можно было проверить тестом.
- Поле частоты работает через существующий механизм формы: те же `contactFields`, та же проверка, то же сохранение введённого при ошибке.
- Без новых библиотек.

**Non-Goals:**

- Явная настройка часового пояса приложения (см. Open Questions).
- Пагинация или ограничение длины блока «Пора связаться»: контактов немного, показываем всех просроченных.
- Проверки в CI: workflow выкатки не трогаем.
- Отметка общения без заметки и отмена нажатия «Связались» кнопкой: ошибочную заметку удаляют как любую другую.

## Decisions

### 1. Данные: два поля в `contacts`

- `contact_frequency` - `text`, может быть `null` («Не задано»), допустимые значения `week`, `month`, `quarter`, `year`. В Drizzle - `text("contact_frequency", { enum: [...] })` плюс `CHECK`-ограничение в базе, чтобы мусор не попал туда даже в обход формы.
- `contact_frequency_set_at` - `timestamptz`, может быть `null`. Момент, когда частоту задали или поменяли на другое значение; при сбросе частоты - `null`. Нужен только для контакта без заметок.

Почему не `pgEnum`: добавить или убрать значение в `text` с `CHECK` - обычная миграция, а у enum-типа в PostgreSQL значения удалять нельзя. Почему не отдельная таблица: одно значение на контакт, связь один к одному не нужна.

Дату последней заметки не храним в `contacts`, а считаем как `max(notes.created_at)`: так она сама правильно меняется при добавлении и удалении заметок, и не нужно держать копию в синхроне.

### 2. Момент задания частоты ставит база одним UPDATE

При создании контакта: `contact_frequency_set_at = now()`, если частота выбрана, иначе `null`.

При изменении контакта - в том же UPDATE, что и остальные поля:

```sql
contact_frequency_set_at = CASE
  WHEN contact_frequency IS NOT DISTINCT FROM <new> THEN contact_frequency_set_at
  WHEN <new> IS NULL THEN NULL
  ELSE now()
END
```

В `SET` PostgreSQL видит старые значения строки, поэтому сравнение идёт со старой частотой. Сохранение формы без смены частоты момент не сдвигает. Время берётся из часов базы, как у `created_at` заметок, - обе даты отсчёта из одного источника.

Альтернатива - прочитать контакт, сравнить в коде и записать: два запроса и гонка между ними, выигрыша нет.

### 3. Расчёт сроков - чистый модуль `src/lib/keep-in-touch.ts`

Модуль без `server-only` и без обращения к базе, импортирует только типы. Функции:

- срок по дате отсчёта и частоте;
- состояние на сегодня: срок, просрочен ли, на сколько дней;
- склонение «день / дня / дней»;
- подпись частоты для интерфейса («раз в месяц»).

Дата отсчёта = дата последней заметки, а если заметок нет - `contact_frequency_set_at`.

Работа с датами: из момента берутся год, месяц и число в часовом поясе процесса (тот же, в котором `format.ts` показывает даты заметок), дальше арифметика на календарных датах через `Date.UTC`: прибавление месяцев с поправкой на последний день месяца, разница в днях - через номера дней от эпохи. Так переход на летнее время и длина месяца не дают ошибок на час или день.

Почему не в SQL: расчёт нужен и в карточке, где заметки уже загружены, и в блоке; одна функция в коде проще, чем одинаковая логика в SQL и в TypeScript, и её легко проверить тестом. Почему без библиотеки дат: нужны только прибавление месяцев и разница в днях.

### 4. Чтение для блока - одна выборка, фильтр и сортировка в коде

Новая функция в `src/lib/data.ts`: контакты с заданной частотой плюс `max(notes.created_at)` через `LEFT JOIN` и `GROUP BY` (индекс по `contact_id` уже есть). Дальше в коде - расчёт состояния, отбор просроченных, сортировка по дням просрочки по убыванию, затем по имени и `id`, как в `listContacts`.

Альтернатива - фильтровать в SQL. Не нужна: контактов с частотой немного, а логика сроков остаётся в одном месте (решение 3).

### 5. Поле в форме - группа переключателей

В `src/components/ui/` нет выпадающего списка. Пять вариантов помещаются в ряд, поэтому поле - группа радиокнопок в виде «таблеток» (как кнопки приложения), стилизованная только токенами. Обычные `<input type="radio" name="contactFrequency">` работают с `FormData` и `defaultValue`/`defaultChecked`, как остальные поля, и доступны с клавиатуры. Пустое значение = «Не задано».

Альтернатива - добавить `select` из shadcn/ui. Отложено: для пяти вариантов переключатель нагляднее и не требует нового компонента.

`contactFrequency` добавляется в `contactFields`, в `contactSchema` - проверка «пусто или одно из четырёх значений», пусто превращается в `null`, иначе ошибка «Выберите частоту из списка».

### 6. Интерфейс - по макету

Макет экранов для телефона и компьютера: https://claude.ai/artifact/Fd6m6F8HWVjxpspLmoigUV (ссылка приватная). Восемь экранов: главная, карточка «срок не наступил», карточка «срок прошёл», форма контакта - каждый для телефона (390 px) и компьютера. Цвета, шрифты, скругления и отступы в макете - из `src/app/tokens.css`, при реализации берутся токены, а не значения из макета.

- Карточка (`src/app/contacts/[id]/page.tsx`): заметки уже загружены, самая новая - первая; состояние считается функцией из решения 3. В списке полей - строка «Общаться» («раз в месяц») и строка «Срок»: «Связаться до 12 ноября 2026» или «Пора связаться · просрочено на 5 дней» цветом `accent-ink` с точкой `accent` перед текстом. В строке «Срок» - кнопка «Связались» (решение 8): на телефоне переносится под текст.
- Главная (`src/app/page.tsx`): над списком - серверный компонент блока со своим `Suspense`, чтобы список не ждал блок. Заголовок «Пора связаться», под ним подложка `powder` с белыми строками. В строке - ссылка на карточку (аватар, имя, «просрочено на N дней» цветом `accent-ink`) и рядом, отдельно от ссылки, кнопка «Связались»: на компьютере справа, на телефоне под текстом. Нет просроченных - компонент ничего не выводит. Блок не зависит от поиска: поиск живёт внутри `ContactBrowser`.
- Форма: поле «Как часто общаться» - после «Место работы», группа из пяти радиокнопок-«таблеток» (решение 5); выбранная - тёмная (`ink`), остальные - серые (`gray`).
- Все даты и подписи формируются на сервере, как даты заметок, чтобы не зависеть от часового пояса браузера.

### 7. Тест расчёта сроков

Тест `src/lib/keep-in-touch.test.ts` на встроенном `node:test` и `node:assert`, запуск через `tsx --test` (новый скрипт `pnpm test`). Покрывает примеры из спецификации: неделя, конец месяца, квартал, 29 февраля, день срока и следующий день, контакт без заметок, склонение. Тест задаёт часовой пояс в самом файле (`process.env.TZ` до первых дат), чтобы результат не зависел от компьютера: переменная окружения в скрипте `pnpm` на Windows не сработает.

### 8. Кнопка «Связались» - обычная заметка

Новое серверное действие `markContacted(contactId)` в `src/app/actions.ts`: проверяет id через `idSchema`, добавляет контакту заметку с текстом «Связались» (текст интерфейса, хранится как обычный текст заметки) и вызывает `revalidateAll()`, никуда не переходя - пользователь остаётся на той же странице. Если контакт уже удалён, заметка не добавляется (вставка с условием, что контакт существует), страница просто обновляется.

Кнопка - маленький компонент: `<form action={markContacted.bind(null, id)}>` и `SubmitButton` в стиле `secondary` с иконкой галочки. Работает без своего клиентского кода, а пока действие выполняется, кнопка недоступна - двойной щелчок не создаёт две заметки. Один компонент используется и в строке блока, и в карточке. Ссылка на карточку и кнопка в строке блока - соседние элементы: кнопку нельзя вкладывать в ссылку.

Почему заметка, а не отдельное поле «когда связались»: так решил владелец - правило «общение = заметка» не меняется, история видна в ленте, заметку можно дописать или удалить. Новых полей в базе нет.

## Risks / Trade-offs

- [Часовой пояс сервера: на сервере, скорее всего, UTC, а пользователь, вероятно, в UTC+3. Заметка, написанная в 01:30 по Москве, по UTC ещё «вчера»] → Срок может сдвинуться на день для заметок, написанных ночью. Ровно так же уже показываются даты заметок, поэтому поведение согласовано; общий вопрос часового пояса - в Open Questions.
- [Дату заметки нельзя указать задним числом: поговорил вчера, записал сегодня - срок от сегодня] → Принято: разница не больше пары дней, указание даты вне рамок изменения.
- [Блок считается на каждый запрос главной] → Одна выборка по контактам с частотой; при сотнях контактов это доли миллисекунды.
- [Тест-раннер - новая часть проекта] → Без новых зависимостей: встроенный в Node.js раннер и уже установленный `tsx`.
- [Нажатие «Связались» ещё раз, например в карточке после блока, добавляет вторую заметку «Связались»] → Принято: подтверждения нет по решению владельца, лишнюю заметку можно удалить. Двойной щелчок защищён тем, что кнопка недоступна, пока сохраняется.
- [Кнопка «Связались» рядом с именем - можно промахнуться и нажать вместо перехода в карточку] → Кнопка - отдельный элемент с подписью и иконкой, не меньше 44 px по высоте; на телефоне стоит под текстом, а не вплотную к имени.

## Migration Plan

1. `pnpm db:generate` создаёт миграцию `drizzle/0002_*.sql`: два новых столбца, оба допускают `null`, плюс `CHECK`. Данные существующих контактов не меняются.
2. При выкатке миграция применяется отдельным шагом до старта нового образа, как обычно.
3. Откат (вручную, если понадобится): предыдущий образ эти столбцы не читает и работает с новой схемой как раньше, поэтому откат образа не требует отката миграции.

## Open Questions

- В каком часовом поясе приложению показывать даты? Сейчас - в поясе сервера, явно он не задан. Если задать, например, `Europe/Moscow`, сдвинутся и даты заметок, и сроки - это отдельная небольшая правка, на требования и задачи этого изменения она не влияет.
