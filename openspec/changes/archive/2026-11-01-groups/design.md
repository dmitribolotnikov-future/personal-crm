# Design

## Context

Мотивация и согласованный объём описаны в `proposal.md`, поведение — в `specs/contact-groups/spec.md`.

Сейчас схема `src/db/schema.ts` содержит `contacts` и `notes`. Серверные чтения сосредоточены в `src/lib/data.ts`, изменения — в `src/app/actions.ts`. Создание и изменение контакта выполняются одной записью без транзакции. `ContactValues` содержит только строки, а `ContactForm` возвращает введённые значения при ошибке через состояние server action.

На главной `ContactBrowser` получает список контактов с сервера и локально ищет по имени. Блок просроченных контактов загружается отдельно. Страницы контакта используют серверное чтение внутри `Suspense`; страница нового контакта пока не читает данные из базы.

В `package.json` тесты запускаются через `tsx --test` и `node:test`; Vitest и Playwright не установлены. Сейчас `pnpm test` запускает только `src/lib/keep-in-touch.test.ts`. Есть workflow выкатки, но нет полного набора проверок PR. По просьбе пользователя настройка e2e и CI отложена. Новые зависимости не добавляем; перенос тестов на Vitest — отдельное согласование, TDD выполняем существующими средствами.

## Goals / Non-Goals

**Goals:**

- Выразить связь «многие ко многим» с целостностью на уровне базы.
- Сохранять контакт и его группы целиком, включая обработку ошибок и одновременных запросов.
- Использовать текущие серверные действия, компоненты и дизайн-токены.
- Дополнить локальную фильтрацию без запросов к базе при каждом выборе группы.

**Non-Goals:**

- Перестройка доступа к данным, отдельный API или новый сервис.
- Изменение расчёта сроков общения и механизма выкатки.
- Установка новых библиотек, миграция инструмента тестирования и настройка e2e/CI в этой фиче.

## Decisions

### 1. Отдельная таблица групп и таблица связей

Добавить `contact_groups` с `id`, `name`, `normalized_name` и обычными временными полями. Добавить `contact_group_memberships` с `contact_id` и `group_id`.

- Составной первичный ключ `(contact_id, group_id)` исключает повторное участие.
- Оба внешних ключа используют `ON DELETE CASCADE`: удаление контакта или группы удаляет только соответствующие строки связей. Удаление группы не затрагивает строки контактов и заметок.
- Индекс по `group_id` поддерживает поиск состава группы и удаление связей. Первичный ключ поддерживает чтение групп контакта.
- На `normalized_name` установить уникальное ограничение; на название — ограничение непустого значения.

Массив названий внутри контакта потребовал бы обновлять множество контактов при переименовании и не обеспечивал бы общую уникальность групп. Связь с устойчивыми идентификаторами сохраняет состав при смене названия.

### 2. Единая нормализация названий на сервере

Общая чистая функция удаляет пробелы по краям через `trim()` и для ключа совпадений приводит текст к нижнему регистру в русской локали. В `name` хранится обрезанное отображаемое название, в `normalized_name` — ключ. Создание и переименование используют одну валидацию Zod. Внутренние пробелы не схлопываются, «е» и «ё» не объединяются: согласованы только регистр и пробелы по краям.

Предварительная проверка помогает показать понятную ошибку, но окончательная защита от параллельного создания — уникальное ограничение базы. Его нарушение преобразуется в ошибку «Группа с таким названием уже есть». При переименовании проверка исключает текущую группу. Неожиданные ошибки базы не маскируются как совпадение названия.

Альтернатива — уникальность по SQL-выражению с `lower` и обрезкой пробелов. Выбран явный ключ, чтобы нормализация в проверках и уникальном ограничении не зависела от различий между правилами пробелов и регистра в JavaScript и настройках PostgreSQL.

### 3. Управление группами на отдельной странице

Добавить `/groups`: список с формой создания, переименованием и подтверждением удаления каждой группы. На главной разместить ссылку «Группы», доступную и при отсутствии контактов. После создания или переименования пользователь остаётся на странице управления. Использовать существующий `ConfirmDeleteDialog`, `Input`, `SubmitButton` и стили через токены; новые библиотеки не нужны.

В форме контакта группы выбираются обычными checkbox-полями в `fieldset`, стилизованными в духе существующего выбора частоты общения. В форме изменения рядом находится «+»: новая группа создаётся и назначается контакту сразу тем же серверным действием, что в карточке. Вложенные HTML-формы не использовать: компонент ввода вызывает своё действие отдельно, не отправляя общую форму контакта. Выбор групп формы сделать управляемым состоянием; успешное создание добавляет новую отметку, сохраняя несохранённые поля и текущие отметки. Во время создания общая отправка блокируется. Отмена общей формы сохраняет уже созданную группу и её назначение — этот момент подтверждён пользователем. Форма нового контакта остаётся с прежним выбором существующих групп.

В карточке названия выводятся компактным списком; сразу после них находится круглая кнопка «+» с доступным названием «Создать новую группу». Она открывает небольшую форму с полем названия, кнопками «Создать» и «Отмена». Фокус переходит в поле; отмена и Escape закрывают форму без записи. После успеха форма закрывается, новая группа появляется у контакта, пользователь остаётся в карточке. Проверки названия общие со страницей `/groups`, при ошибке ввод сохраняется. Создание группы и её назначение контакту выполняются одной транзакцией с блокировкой контакта; ошибка назначения не оставляет пустую новую группу. У контакта без групп остаётся кнопка, пустой список не выводится. Группы в управлении, форме, карточке и фильтре сортируются по названию, затем по `id` для устойчивого порядка.

На `/groups` название каждой группы становится ссылкой на `/groups/[id]`. Новая страница загружает группу и её участников под `Suspense`, используя `connection()`; участников читать одним соединением таблиц с условием по `group_id`, сортировать по имени и `id`. Составной ключ связей исключает повтор контакта в одной группе. У пустой группы показать сообщение; отсутствующий или некорректный идентификатор ведёт в `notFound()`.

В карточке под группами добавить «Настроить группы» со ссылкой `/contacts/[id]/edit#contact-groups-[id]`. У соответствующего `fieldset` формы изменения — устойчивый идентификатор с `id` контакта и отступ для прокрутки. После появления асинхронного блока формы проверить фрагмент URL и прокрутить к нему; это также поддерживает прямую ссылку и сохранённые Next.js страницы.

### 4. Контакт и набор групп сохраняются транзакцией

Дополнить значения формы массивом `groupIds`, сохранив текущие строковые поля. Читать повторяющиеся значения через `FormData.getAll`, проверять положительные целочисленные идентификаторы и удалять повторы. Ошибки должны возвращать и текстовые значения, и выбранные группы.

`createContact` и `updateContact` выполняют запись контакта и замену его связей в одной транзакции. Внутри неё проверить существование выбранных групп; защитить найденные группы блокировкой от удаления до завершения записи. При изменении блокировать строку контакта, чтобы параллельные сохранения его набора групп не смешивались. Если выбранной группы уже нет, вернуть понятную ошибку без частичного сохранения; пользователь исправляет выбор после обновления списка групп.

Изменение частоты общения продолжает использовать существующую проверку прежнего значения: правка только групп не меняет `contactFrequencySetAt`. Пустой набор снимает все связи. Ошибка откатывает всю операцию. После успеха использовать существующую общую инвалидацию страниц и переход в карточку.

Отдельное сохранение групп после контакта было бы проще, но могло бы оставить изменённые поля со старым или частичным составом групп.

### 5. Чтение без отдельного запроса для каждой строки

В `src/lib/data.ts` добавить чтение всех групп и групп одного контакта. Для главной получать контакты, группы и связи пакетно, собирать массив `groupIds` у каждого элемента `ContactSummary` на сервере. Не размножать строки контактов соединением «многие ко многим» в итоговом списке.

Формы добавления и изменения загружают доступные группы на сервере; страница добавления получает асинхронный блок под `Suspense`, как существующая страница изменения. Карточка загружает группы вместе с прочими данными. Все новые чтения сохраняют текущий подход с `connection()` и не обращаются к базе при сборке.

### 6. Фильтр дополняет существующий поиск

В `ContactBrowser` использовать раскрывающийся фильтр с checkbox-полями групп. Пустой набор выбранных групп означает «Все контакты»; кнопка «Все контакты» снимает выбор без сброса имени. Контакт виден, если входит хотя бы в одну выбранную группу и подходит под поиск по имени. Контакты фильтруются один раз, поэтому участие в нескольких выбранных группах не даёт повторов. Закрытая строка показывает названия выбранных групп, при нехватке места текст обрезается. Использовать `details`/`summary`, собственную иконку `ChevronDown` и внутренний отступ `px-5`, чтобы стрелка не прижималась к правому краю. Открытый фильтр поясняет правило объединения. Список раскрывается в потоке страницы и остаётся открытым при отметке нескольких групп; управление доступно с клавиатуры. Правила поиска, включая приравнивание «ё» к «е», и порядок контактов сохраняются. Логику объединения и поиска вынести в чистую функцию для TDD.

Проверка пустого общего списка не должна скрывать управление группами. Пустые группы и отсутствие совпадений отображать понятным сообщением с доступными поиском и выбором групп. Если после обновления данных выбранных групп больше нет, убрать только отсутствующие идентификаторы; оставшиеся продолжат действовать. Когда выбор опустеет, использовать «Все контакты».

Состояние фильтра остаётся локальным, как текущий поиск; сохранение в URL и между посещениями не добавляем. Блок `OverdueContacts` остаётся отдельным и получает все просроченные контакты, как требует действующая спека.

В строке контакта общего списка под именем и описанием показывать компактные подписи групп: пересечение его `groupIds` с текущими выбранными и существующими группами. Список доступных групп уже отсортирован на сервере; подписи сохраняют этот порядок. При пустом выборе блок не выводить, поиск только по имени его не включает. Подписи обновляются вместе с текущим состоянием галочек. Использовать существующие токены и данные в `ContactBrowser`, дополнительных запросов к базе не добавлять; выбор подписей вынести в чистую функцию для TDD.

### 7. Проверки существующим инструментом

Для новой логики сначала написать падающие тесты, затем реализацию и убедиться, что тесты стали зелёными. Проверить нормализацию и валидацию названий, разбор массива идентификаторов, пересечение поиска и группы. Для серверных операций проверить важные развилки с контролируемыми зависимостями: совпадение названия, несуществующая группа, откат при ошибке и сохранение набора целиком. Не вводить новую архитектуру только ради тестов.

Обновить `pnpm test`, чтобы он запускал существующие и новые тестовые файлы через уже установленный `tsx`; не ограничиваться прежним единственным файлом. Ограничения базы, удаление связей и работу интерфейса проверить вручную на локальном PostgreSQL в Docker. Это не e2e-автоматизация. Ручные шаги и фактические результаты сохранить при выполнении задач.

## Risks / Trade-offs

- Одновременное создание одинаковых названий → уникальный ключ в базе и обработка его конкретной ошибки.
- Группа удалена между открытием формы и сохранением → проверка в транзакции и блокировка существующих выбранных групп; ошибка не сохраняет часть контакта.
- Параллельная правка групп одного контакта → блокировка контакта и атомарная замена набора; последняя завершённая правка сохраняется целиком.
- Загружаем все связи для локальной фильтрации → соответствует текущей загрузке всех контактов; при существенном росте объёма серверную фильтрацию следует планировать отдельно.
- Автоматическая проверка браузера отложена → ручная приёмка всех пользовательских сценариев обязательна для завершения фичи.
- Текущий test runner отличается от указанного в стеке Vitest → используем уже существующий инструмент без новой зависимости; его замену не смешиваем с группами.

## Migration Plan

1. Добавить таблицы, ограничения и индекс в Drizzle; сгенерировать и проверить новую миграцию, snapshot и журнал. Старые таблицы и данные не переписываются, предустановленные группы не создаются.
2. На локальной базе применить миграцию командой `pnpm db:migrate`, проверить старые контакты, затем выполнить ручную приёмку из `tasks.md`.
3. Доставка через обычную ветку и PR. e2e и новые проверки CI в этом изменении не настраиваются, существующий workflow выкатки не ослабляется.
4. При выкатке штатный разовый контейнер применяет миграцию до нового образа. При ошибке миграции новый образ не стартует. После запуска проверить `/health` и сценарий создания группы, назначения и фильтрации.
5. При красном smoke сообщить пользователю. Автоматический откат не добавлять и самостоятельно откат не выполнять. Старая версия приложения совместима с добавленными таблицами; при ручном откате образа таблицы и данные групп остаются в базе, обратная миграция с удалением данных не выполняется.
