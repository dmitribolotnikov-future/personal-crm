# Личная CRM

Приложение, где я веду контакты людей, которых знаю лично. Подробнее: `specs/01-продуктовая-идея.md`.

## Что нужно установить

- Node.js (LTS) и pnpm
- Docker Desktop: в нём работает база данных

## Работа со спеками через OpenSpec

OpenSpec помогает сначала согласовать требования и план, а затем реализовать изменение. Требования лежат в `openspec/specs/`, планы текущих изменений — в `openspec/changes/`, завершённые изменения — в `openspec/changes/archive/`.

В проект подключены навыки OpenSpec для Codex в `.agents/skills/`. После подключения перезапустите Codex и откройте проект заново. В приложении Codex выберите нужный навык в разделе Skills; в CLI или расширении редактора можно написать:

- `$openspec-explore` — обсудить идею и уточнить требования;
- `$openspec-propose` — подготовить предложение, спеку, технический план и задачи;
- `$openspec-update-change` — внести правки в подготовленные документы;
- `$openspec-apply-change` — реализовать согласованные задачи;
- `$openspec-sync-specs` — перенести изменения требований в основные спеки;
- `$openspec-archive-change` — отправить завершённое изменение в архив.

Например: `$openspec-propose Добавить поиск контактов по заметкам`. Сначала проверьте и согласуйте документы, затем запускайте реализацию.

Тексты документов OpenSpec пишутся на русском: это задано в `openspec/config.yaml`. Служебные заголовки, ключевые слова формата (`Requirement`, `Scenario`, `SHALL`, `MUST`, `WHEN`, `THEN`), имена файлов и код остаются на английском.

CLI устанавливается один раз на компьютер по [официальной инструкции](https://openspec.dev/docs/installation). Для Windows в PowerShell:

```powershell
irm https://openspec.dev/cli/install.ps1 | iex
```

После установки откройте новый терминал. Проверить версию и спеки проекта:

```powershell
openspec --version
openspec validate --all --strict --no-interactive
```

Обновить CLI: `openspec install`. Обновить созданные им навыки проекта: `openspec update`.

## База данных

База — PostgreSQL в Docker. Настройки подключения лежат в файле `.env`. Его нет в git, потому что там пароль.

**Первый запуск на новом компьютере.** Скопируйте `.env.example` в `.env` и заполните значения.

**Запустить базу** (Docker Desktop должен быть открыт):

```
docker compose up -d
```

**Проверить, что база работает:**

```
docker compose ps
```

В колонке `STATUS` должно быть `healthy`.

**Остановить базу:**

```
docker compose stop
```

Данные при остановке сохраняются. Они хранятся в Docker-томе `personal-crm_db-data`.

## Приложение

Приложение берёт настройки подключения к базе из тех же переменных `POSTGRES_*` в `.env`, что и Docker. Отдельно прописывать подключение не нужно.

**Первый запуск на новом компьютере** (база должна быть запущена):

```
pnpm install
pnpm db:migrate
```

Первая команда ставит библиотеки, вторая создаёт таблицы в базе.

**Запустить приложение:**

```
pnpm dev
```

Затем откройте в браузере http://localhost:3000. Остановить — `Ctrl+C` в терминале.

## Тестовые данные

Чтобы посмотреть приложение на большом списке, можно загрузить 1000 выдуманных контактов с заметками (база должна быть запущена):

```
pnpm db:seed
```

Контакты добавляются к уже существующим, ваши записи не трогаются. Повторный запуск ничего не добавит: скрипт заметит, что тестовые контакты уже загружены. Почты у тестовых контактов — на зарезервированных доменах `example.com`, `example.org`, `example.net`, поэтому совпасть с адресом реального человека не могут.

## Группы контактов

1. На главной нажмите «Группы». Введите название и нажмите «Создать группу». Группу можно создать без контактов. Названия с разным регистром и пробелами по краям считаются одинаковыми.
2. Чтобы переименовать группу, измените её название в списке и нажмите «Сохранить». Участники группы останутся прежними.
3. Чтобы удалить группу, нажмите «Удалить» и подтвердите. Кнопка «Отмена» сохраняет группу. Удаление снимает только эту группу с контактов; контакты, заметки и остальные группы сохраняются.
4. В форме добавления или изменения контакта выберите нужные группы в блоке «Группы» и нажмите общую кнопку сохранения. Можно выбрать несколько групп, снять одну или все. При ошибке другого поля выбор остаётся. После сохранения группы видны в карточке и при повторном открытии формы. «Отмена» оставляет прежний выбор существующих групп.
5. На главной раскройте фильтр «Группы» и отметьте нужные группы галочками. В списке будут люди, входящие хотя бы в одну выбранную группу: «Друзья» и «Теннис» покажут и друзей, и тех, с кем вы играете в теннис. Человек в обеих группах показан один раз. Поиск по имени работает внутри этого списка. Можно снять отдельную галочку или нажать «Все контакты», чтобы снять весь выбор, сохранив введённое имя. Поиск и группы не меняют блок «Пора связаться»: в нём остаются все просроченные контакты. Правка только групп не сдвигает срок общения.
6. На странице «Группы» нажмите название группы — откроется страница со всеми её участниками. Нажатие на участника открывает его карточку. У группы без участников показано соответствующее сообщение; «Все группы» возвращает в общий список групп.

При выборе групп в фильтре у каждого контакта в общем списке показаны подписи только тех выбранных групп, в которые он входит. Например, при выборе «Друзья» и «Теннис» у человека из обеих групп видны обе подписи, а у человека только из «Друзья» — одна. Остальные группы скрыты. После сброса фильтра подписи исчезают, в том числе при заполненном поиске по имени.

Группы и их состав сохраняются в общей базе и видны в другом браузере.

Создать группу можно прямо в карточке контакта: нажмите «+» рядом с группами, введите название в появившееся поле и нажмите «Создать». Новая группа сразу назначится этому контакту и появится в карточке; остальные группы сохранятся. Кнопка доступна и у контакта без групп. «Отмена» или Escape закрывают поле без создания группы. При ошибке названия введённый текст сохраняется.

Такой же «+» есть в форме «Изменить контакт». Новая группа создаётся и назначается сразу, при этом введённые в другие поля значения и текущие галочки сохраняются в форме. Уже созданная группа останется у контакта даже после «Отмена» всей формы. Общая кнопка «Сохранить» применяет остальные изменения.

В карточке под группами нажмите «Настроить группы»: откроется форма изменения контакта и сразу прокрутится к выбору групп.

## Проверки приложения

Автоматические проверки покрывают сроки «когда пора связаться», значения частоты и сохранение выбора при ошибке формы, отбор и порядок просроченных контактов, названия групп, разбор выбранных групп, ошибки и атомарность серверного сохранения с контролируемыми зависимостями, фильтрацию вместе с поиском. База для них не нужна:

```
pnpm test
```

В конце Vitest должен показать, что все тесты прошли (`passed`), без `failed`. При ошибке выше будет видно, какая проверка не прошла.

Отдельно код проверяется командами `pnpm lint` (стиль и очевидные ошибки), `pnpm format:check` (форматирование), `pnpm typecheck` (типы) и `pnpm build` (сборка, как на сервере). Исправить форматирование можно командой `pnpm format`.

### CI и слияние изменений

На каждом PR GitHub Actions запускает шесть проверок: **Lint**, **Format**, **Types**, **Vitest**, **Playwright** и **Docker image**. Playwright использует отдельный временный PostgreSQL в Docker, без подмены запросов или базы. Образ в PR только собирается; публикация и выкатка происходят после слияния в `main`.

Ветка `main` защищена, в том числе для администратора: изменения попадают в неё только через PR со всеми шестью зелёными проверками и с учётом актуальной `main`. Прямой push, force push и удаление ветки запрещены. Настройки защиты хранятся в GitHub, отдельно от файлов репозитория.

Автовлитие разрешено в настройках репозитория. Для каждого нового PR его нужно включать отдельно: `gh pr merge --auto --squash`. После успешных обязательных проверок GitHub сам вольёт PR. Проверить результат можно внизу страницы PR: видны шесть проверок и состояние автовлития. При ошибке Playwright отчёт и трассировка доступны в разделе **Artifacts** запуска CI в течение семи дней.

### Сквозные тесты

Тест в `e2e/main-scenario.spec.ts` открывает приложение в настоящем браузере: добавляет контакты, находит нужного по имени, добавляет заметку после разговора и проверяет её после перезагрузки. Затем в отдельной браузерной сессии проверяет тот же список контактов и сохранённую заметку. Запросы и база не подменяются.

В `e2e/keep-in-touch.spec.ts` добавлены пять путей: создание контакта с частотой и без неё, изменение и сброс частоты, блок «Пора связаться» с поиском и другой сессией браузера, кнопка «Связались» с правкой и удалением заметки, обычные заметки с пересчётом срока. Перед запуском браузера отдельный тест создаёт контакты и заметку в старой схеме базы, применяет настоящие миграции и проверяет сохранность данных. Карточка старого контакта затем проверяется в браузере. Полное соответствие всех 34 сценариев спеки тестам — в [таблице покрытия keep-in-touch](openspec/specs/keep-in-touch/test-coverage.md).

Один раз установите браузер для Playwright:

```
pnpm exec playwright install chromium
```

Откройте Docker Desktop и запустите:

```
pnpm test:e2e
```

Команда сама создаёт временный PostgreSQL в Docker, применяет миграции, собирает приложение и запускает его на http://127.0.0.1:3100. Порт 3100 должен быть свободен. Для базы выбирается свободный локальный порт; настройки вашей базы не нужны. У временной базы нет пароля: доступ разрешён только с этого компьютера. По окончании, в том числе при падении теста, временный контейнер вместе с тестовыми данными удаляется. Обычная база приложения сохраняется.

Успешный результат — сообщение `Contact frequency migration: passed` и `6 passed` от Playwright. Посмотреть шаги в окне браузера: `pnpm test:e2e --headed`. При падении сохраняются снимок экрана и трассировка в `test-results/`; HTML-отчёт можно открыть командой `pnpm exec playwright show-report`. Эта же команда `pnpm test:e2e` выполняется в CI на каждом PR.

## Изменения в структуре базы

Таблицы описаны в коде: `src/db/schema.ts`. Если схема поменялась:

```
pnpm db:generate
pnpm db:migrate
```

Первая команда создаёт файл миграции в папке `drizzle/` (его нужно сохранить в git), вторая применяет его к базе. После `git pull` достаточно `pnpm db:migrate`.

На сервере миграции применяются сами при выкатке, руками ничего запускать не нужно.

Группы хранятся в таблицах `contact_groups` и `contact_group_memberships` общей базы PostgreSQL. Миграция групп только добавляет таблицы: прежние контакты и заметки сохраняются, группы старым контактам автоматически не назначаются. Удаление группы снимает её с контактов, сохраняя сами контакты, заметки и остальные группы.

## Выкатка на сервер

Приложение работает на сервере по адресу https://app.lichnocrm.ru.

**Как выкатить новую версию:** открыть PR в `main` и включить автовлитие. После шести зелёных проверок CI PR вольётся в `main`. Дальше всё происходит само:

1. GitHub Actions собирает образ приложения и кладёт его в GHCR. Метка образа — номер коммита.
2. Подключается к серверу пользователем `deploy`, копирует туда папку `deploy/` и запускает `deploy/deploy.sh`. Скрипт по шагам:
   - первым шагом сохраняет бэкап текущей базы в `/srv/personal-crm/backups/`. В имени файла — время UTC и версия приложения, которая стояла **до выкатки**. Версия берётся из фактического контейнера, даже если предыдущая выкатка прервалась. Если бэкап не удалось создать или прочитать, выкатка останавливается до загрузки нового образа и миграций;
   - загружает новый образ;
   - запускает базу, если она не запущена;
   - разовым контейнером из нового образа применяет миграции. Если миграции упали, выкатка останавливается, а старая версия продолжает работать;
   - запускает новую версию вместо старой;
   - проверяет, что https://app.lichnocrm.ru/health отвечает `{"status":"ok"}`.
3. Убирает старые образы: на сервере остаются только текущий и предыдущий.

**Как следить:** вкладка **Actions** в репозитории на GitHub. Зелёная галочка — новая версия на сервере. Красный крестик — выкатка упала: откройте её и посмотрите, на каком шаге. Сам скрипт ничего не откатывает.

**Как проверить руками:** открыть https://app.lichnocrm.ru/health — должно быть `{"status":"ok"}`. Потом открыть https://app.lichnocrm.ru и посмотреть на сами контакты.

### Что лежит на сервере

Зайти на сервер: `ssh crm`. Всё приложение — в папке `/srv/personal-crm`:

- `compose.yaml` и скрипты `*.sh` — их кладёт выкатка из папки `deploy/` в репо. Руками на сервере их не правят: правка в репо, PR и слияние после зелёного CI.
- `.env` — настройки базы с паролем. Его нет в git, читать его может только пользователь `deploy`.
- `releases` — какие образы на сервере: первая строка — предыдущий, последняя — текущий.
- `backups/` — бэкапы базы перед каждой выкаткой и перед восстановлением. Доступ к папке — только у `deploy`, к файлам — только у владельца.
- `operations.lock` — блокировка: выкатка и восстановление не могут выполняться одновременно.

Данные базы хранятся в Docker-томе `prod_db-data` и переживают выкатки и перезагрузки сервера.

**Файл `.env` на сервере** — три строки:

```
POSTGRES_USER=crm
POSTGRES_PASSWORD=<длинный случайный пароль>
POSTGRES_DB=crm
```

Открыть его для правки (на сервере, после `ssh crm`):

```
sudo -u deploy bash -c 'umask 077 && nano /srv/personal-crm/.env'
```

Пароль база запоминает при самом первом запуске. Если потом поменять его в `.env`, база новый пароль не примет.

### Откат на предыдущую версию

Только вручную, сам скрипт выкатки никогда не откатывает:

```
ssh crm sudo -u deploy bash /srv/personal-crm/rollback.sh
```

Предыдущая версия запустится снова. Миграции при откате не отменяются: если новая версия поменяла структуру базы, старая может с ней не заработать.

### Бэкапы базы

Бэкап содержит структуру и данные всей базы приложения, включая историю миграций. Формат — сжатый архив PostgreSQL (`.dump`). Например:

```
20261109T120000Z_d9d5f13_pre-deploy_aB12cD.dump
```

Здесь `d9d5f13` — версия приложения **до выкатки** (в настоящем имени — полный SHA), `pre-deploy` — копия перед выкаткой; `pre-restore` — копия перед восстановлением. Последняя часть делает имя уникальным. Незавершённые копии имеют окончание `.partial`; их нельзя использовать для восстановления. Скрипт проверяет чтение всего архива до публикации готового файла. Эта проверка не заменяет настоящее восстановление.

Бэкап снимается с уже работающей базы; если база недоступна или текущий контейнер приложения отсутствует, выкатка останавливается. Для самого первого запуска на пустом сервере сначала нужно подготовить работающую базу и контейнер приложения.

**Проверка после выкатки:** в логе Deploy шаг `Database backup before deployment` должен стоять перед `Image` и `Migrations`, а строка `Backup saved:` — содержать путь к файлу со старой версией. На сервере можно посмотреть список и размеры копий:

```
ssh crm
sudo -u deploy ls -lh /srv/personal-crm/backups/
sudo -u deploy du -sh /srv/personal-crm/backups/
```

Бэкапы автоматически не удаляются. Их размер проверяется командой выше; нужные копии можно забрать с сервера отдельно. Новые настройки в `.env` не нужны.

### Восстановление базы из бэкапа

Восстановление запускает только человек. Оно заменит **всю текущую базу** содержимым выбранного файла. Сначала зайдите на сервер, затем укажите полный путь к нужному `.dump`:

```
ssh crm
sudo -u deploy bash /srv/personal-crm/restore.sh /srv/personal-crm/backups/<backup-file>.dump
```

Скрипт проверит чтение архива, покажет полный путь, имя базы проекта `prod` и текущую версию приложения. Перед заменой базы он попросит ввести `yes`. Любой другой ответ отменит восстановление.

После подтверждения скрипт:

1. Сохранит копию текущей базы с пометкой `pre-restore`. Если копия не получилась, остановится до остановки приложения и удаления базы.
2. Остановит приложение прода.
3. Удалит базу, создаст заново пустую и загрузит выбранный бэкап. Остальные базы и Docker-том не удаляются.
4. Запустит тот же контейнер приложения и проверит `/health`. Образ приложения, файл `releases` и миграции не меняются; миграции не запускаются.

Пока идёт замена базы, приложение недоступно. Если замена базы завершится ошибкой, приложение останется остановленным; автоматического восстановления нет. Сохранённая копия `pre-restore` останется на сервере. Перед следующей попыткой нужно разобраться с ошибкой: повторный запуск требует доступной текущей базы для новой страховочной копии. Если ошибка произошла уже при запуске приложения или проверке `/health`, база восстановлена, но нужно отдельно проверить состояние приложения. Версия приложения должна подходить структуре выбранного бэкапа: скрипт её не переключает.

**Как проверить руками:** сначала запустите restore и ответьте `no` — база и приложение должны остаться прежними. Для проверки настоящего восстановления выберите копию, запомните версию контейнера и создайте в CRM временный контакт. Повторите restore с этой копией и подтвердите `yes`: временный контакт должен исчезнуть, а контакты и заметки из копии — остаться. Само восстановление выполняйте только тогда, когда готовы заменить текущие данные выбранной копией.

Версию и контейнер до и после можно сравнить на сервере:

```
sudo -u deploy docker ps -a --filter label=com.docker.compose.project=prod --filter label=com.docker.compose.service=app --format '{{.ID}} {{.Image}}'
```

Они должны совпасть. В конце restore должно быть `app version unchanged`, в папке `backups/` — новая копия `pre-restore`, а https://app.lichnocrm.ru/health должен отвечать `{"status":"ok"}`. Затем откройте CRM и проверьте контакты и заметки.
